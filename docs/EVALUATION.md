# การทดสอบความแรงและเกณฑ์รับ net

เอกสารนี้กำหนดขั้นตอนมาตรฐานในการตัดสินว่า net ใหม่ **แรงกว่า** net เดิมหรือไม่
ซึ่งเป็นเงื่อนไขบังคับก่อนนำ net เข้า `nets/` (กฎเหล็กข้อ 2 ใน `CLAUDE.md`)

## 1. หลักการ

- ค่า loss ที่ต่ำลงไม่เป็นหลักฐานว่าเล่นเก่งขึ้น (net อาจจำข้อมูลได้ หรือข้อมูลเปลี่ยนไป
  ทำให้ loss เปรียบเทียบข้ามชุดข้อมูลไม่ได้)
- ตัวตัดสินคือ **ผลการแข่งจริง** ระหว่าง engine ที่ใช้ net ใหม่กับ engine ที่ใช้ net เดิม
- ผลต้องเกินช่วงความคลาดเคลื่อน (ขอบล่างของช่วง ± ต้องมากกว่า 0)
- รายงานผลตามจริง รวมถึงการทดลองที่ไม่ผ่าน (กฎเหล็กข้อ 7)

## 2. เครื่องมือ

| เครื่องมือ | หมายเหตุ |
|---|---|
| `fastchess` v1.8.3-alpha | ไม่อยู่ใน repository ดาวน์โหลด `fastchess-windows-x86-64.zip` จาก [releases](https://github.com/Disservin/fastchess/releases) |
| ชุดตำแหน่งเปิดเกม | สร้างด้วย `engine/examples/book.rs` |
| ไบนารี engine | `cargo build --release -p wyrdmate-engine` |

## 3. ขั้นตอน

### 3.1 สร้างชุดตำแหน่งเปิดเกม

```bash
cargo run --release -p wyrdmate-engine --example book -- 300 99 data/book.epd
```

ได้ 300 ตำแหน่งเปิดเกมแบบสุ่มที่สมดุล (seed 99) ใช้ชุดเดียวกันทุกการแข่งเพื่อให้เปรียบเทียบกันได้

### 3.2 รันการแข่ง

รันจาก PowerShell:

```text
fastchess -engine name=new cmd=<engine.exe> option.EvalFile=<quantised.bin> -engine name=old cmd=<engine.exe>
  -each proto=uci tc=inf nodes=10000 option.Nodes=10000 -openings file=data/book.epd format=epd order=random
  -rounds 300 -games 2 -repeat -concurrency 4 -maxmoves 120
  -draw movenumber=30 movecount=8 score=10 -resign movecount=4 score=800
```

| พารามิเตอร์ | ความหมาย |
|---|---|
| `nodes=10000`, `option.Nodes=10000` | จำกัดทั้งสองฝ่ายที่ 10,000 node ต่อตา (ไม่ใช้เวลาเป็นตัวจำกัด เพื่อให้ผลไม่ขึ้นกับเครื่อง) |
| `-rounds 300 -games 2 -repeat` | 300 ตำแหน่ง × 2 เกม (สลับสี) = **600 เกม** |
| `-maxmoves 120` | ตัดสินเสมอเมื่อครบ 120 ตา |
| `-draw ...` | ตัดสินเสมอเมื่อคะแนนใกล้ 0 นานพอ |
| `-resign ...` | ตัดสินแพ้เมื่อได้เปรียบเกิน 800 เซนติเบี้ย 4 ตาติดกัน |

เมื่อเทียบกับ engine นับมูลค่าหมาก ให้ฝั่ง `old` ไม่ใส่ `option.EvalFile`

### 3.2.1 สคริปต์ที่รันให้

`scripts/ab.ps1` ทำขั้นตอนข้อ 3.2 ให้ครบ: build engine รุ่นใหม่/เก่าจาก git ref (เก็บไบนารีไว้ที่ `tools/engines/`),
สร้างชุดตำแหน่งเปิดถ้ายังไม่มี, แข่งด้วย fastchess และพิมพ์ผล พร้อมบรรทัด `VERDICT` ตามกฎ (ขอบล่างของ Elo ต้องมากกว่า 0)

```powershell
powershell -File scripts/ab.ps1                      # โค้ดที่ยังไม่ commit เทียบกับ HEAD
powershell -File scripts/ab.ps1 -New HEAD -Old c81e99b
powershell -File scripts/ab.ps1 -Net nets/wyrd-v.bin -OldNet nets/wyrd-iv.bin   # net เทียบ net (engine ตัวเดียวกัน)
```

บันทึกผลที่ `logs/ab-<ชื่อ>.txt` และ `.pgn` (git-ignored) พารามิเตอร์: `-Nodes` (ค่าเริ่มต้น 10,000), `-Rounds` (300 = 600 เกม),
`-Concurrency`, `-Tag` (ตั้งชื่อไฟล์ผล) ต้องมี `tools/fastchess` ตามที่ระบุใน CLAUDE.md

### 3.3 ตรวจความถูกต้องของการอ่าน net (ก่อนแข่ง)

```bash
cargo run --release -p wyrdmate-engine --example validate -- <net.bin> <data.txt>
```

ค่าสหสัมพันธ์ประมาณ 0.83 หมายความว่า engine อ่าน net ได้ตรงกับ trainer
หากต่ำผิดปกติ แสดงว่ามีความไม่ตรงกันของโครงสร้างหรือการแมปฟีเจอร์ ให้แก้ก่อนแข่ง

## 4. เกณฑ์การรับ net

net ใหม่จะถูกรับก็ต่อเมื่อครบทุกข้อ:

1. แข่งกับ net ปัจจุบัน อย่างน้อยหลายร้อยเกม (ที่ผ่านมาใช้ 600 เกม)
2. Elo ที่วัดได้ **ขอบล่างของช่วงความคลาดเคลื่อนมากกว่า 0**
3. มีบันทึกที่มาครบใน `nets/RECORDS.md` (ดูข้อ 5)
4. เพิ่มแถวผลแข่งใน `docs/progress/data.json` และสร้างกราฟใหม่

## 5. ข้อมูลที่ต้องบันทึก

ใน `nets/RECORDS.md` (กฎเหล็กข้อ 1):

- git commit ของเครื่องมือที่ใช้ และ rev ของ bullet
- อาร์กิวเมนต์ของ `wyrdmate-trainer` ทั้งหมด
- ข้อมูลเทรน: seed, nodes, จำนวนเกม, net ที่ใช้เล่นสร้างข้อมูล, จำนวนตำแหน่ง
- ผลแข่ง: คู่แข่ง, จำนวนเกม, Elo ± ความคลาดเคลื่อน

ใน `docs/progress/data.json`: เพิ่มแถวใน `matches` ทุกครั้งที่แข่งเสร็จ
(`net, vs, elo, err, games, accepted, finished, commit`) และเพิ่มชุดข้อมูลใน `loss` เมื่อการเทรนนั้นควรเก็บไว้
จากนั้นสร้างกราฟใหม่:

```text
powershell -File scripts/make-progress-svg.ps1
```

## 7. ข้อจำกัดที่ต้องระบุเมื่อรายงานผล

- วัดเทียบกับ engine รุ่นก่อนของโครงการเอง **ยังไม่เคยเทียบกับ engine ภายนอก** จึงยังไม่มีค่า Elo สัมบูรณ์
- ผลวัดที่ 10,000 node ต่อตา ที่ node จำนวนอื่นผลอาจต่างออกไป
- ชุดตำแหน่งเปิดเกมสร้างจาก seed เดียว

**ข้อจำกัดของตัวเลขนี้ (ต้องระบุเมื่ออ้างอิง):**

- `UCI_Elo` ของ Stockfish ปรับเทียบไว้ที่ time control ยาวกว่าที่ใช้ที่นี่มาก และเป็นการ "ทำให้อ่อนลงโดยตั้งใจ"
  (บางครั้งเลือกท่าที่ไม่ดีที่สุด) ไม่ใช่ engine ที่อ่อนจริง จึงไม่ใช่ Elo มาตรฐาน (CCRL/FIDE) ใช้เป็นหลักยึดหยาบเท่านั้น
- ผลของ Stockfish แต่ละตัวห่างกันน้อยกว่าค่าที่ตั้ง: ตั้งห่างกัน 200 แต่วัดได้ ~90–110 (1500→1700→1900→2100→2300) แปลว่าที่ time control นี้
  มาตรา `UCI_Elo` ถูกบีบ ช่วง 1320→1500 ใกล้ค่าที่ตั้ง (วัด 173 จาก 180) จึงใช้แปลงช่วงนี้ แต่ค่าเทียบเป็นประมาณยิ่งไกลจากช่วงนี้ยิ่งไม่แม่น
- ขั้นต่ำสุดของ `UCI_Elo` คือ 1320 ระดับต่ำกว่านั้นของเราอ่านค่าเฉพาะไม่ได้
- ได้คะแนนเท่ากันในสองคู่ (6,400 กับ 12,800; 1,600 กับ 3,200) ตรงกับตารางข้อ 8 ยังไม่ทราบสาเหตุ
  (เบาะแสสำหรับงานปรับปรุง search ใน ROADMAP)
- วัดบน search รุ่นปัจจุบันเท่านั้น หากเปลี่ยน search ต้องวัดซ้ำ

- `datagen` เรียก `Searcher` เหมือนเดิมแต่ไม่ส่งประวัติเกม จึงเห็นเฉพาะการซ้ำภายใน search ของตัวเอง
  (ข้อมูลเทรนรอบถัดไปจะต่างจากรอบก่อนเล็กน้อย ต้องบันทึก commit ของ datagen ตามกฎเหล็กข้อ 1)
- เว็บเดโม (`web/`) ส่งแค่ FEN ไม่ส่งประวัติ จึงเห็นการซ้ำเฉพาะภายใน search เท่านั้น

### s3 เทียบ s2 ที่ node ต่างกัน (`wyrd-iv` ทั้งสองฝั่ง, 600 เกมต่อระดับ)

| `Nodes` | Elo | ± | ผลตามกฎ |
|---:|---:|---:|---|
| 1,000 | +16 | 24 | ไม่ผ่าน (ขอบล่าง < 0) |
| 10,000 | +79 | 25 | ผ่าน |
| 50,000 | +92 | 24 | ผ่าน |

- ผลดีขึ้นเมื่อ node มากขึ้น สอดคล้องกับที่ลำดับท่าที่ดีช่วยให้ตัดกิ่งได้มากในการค้นลึก ที่ 1,000 node ยังแยกจากศูนย์ไม่ได้
- ท่าดีสุดของรอบก่อนไปก่อนที่ราก: โค้ดเดิมจัดลำดับท่าที่รากใหม่ด้วยค่าคงที่ทุกรอบ ทำให้ท่าดีสุดที่ย้ายไปหน้าสุดถูกสลับกลับ
  แก้อย่างเดียวได้ +15 ± 20 (600 เกม, 10k node) ไม่ผ่านกฎเมื่อวัดเดี่ยว ๆ จึงรับเข้ามาพร้อมกับ killer/history เป็นชุดเดียว
- ความเร็ว: จับเวลา 3,000,000 node ได้ ~660–700 ms ทั้ง s2 และ s3 (เท่ากันในค่าคลาดเคลื่อน) หลังเปลี่ยนไปใช้ `sort_by_cached_key`
  ก่อนหน้านั้น (คำนวณคะแนนท่าซ้ำในการเรียงลำดับ) s3 ช้ากว่า ~23%
- หน่วยความจำเพิ่ม: ตาราง history 16 KB (`i16`) + killer 128 × 2 ท่า ต้องนับรวมในงบ RAM ของเฟิร์มแวร์
- ตัวเลขข้อ 8 และ 9 (ตารางระดับ, เทียบ Stockfish) เป็นของ s1 ยังไม่ได้วัดซ้ำ

### ลองแล้วไม่รับ: PVS (principal variation search)

เทียบ s3 ตัวเดียวกัน 600 เกมต่อระดับ: 1,000 node **−27 ± 23**, 10,000 node **−3 ± 22**, 50,000 node **+34 ± 22**
ที่ 10k (ระดับอ้างอิงของ A/B) ไม่ต่างจากศูนย์ และที่ node ต่ำแย่ลง (การค้นซ้ำกินจำนวน node) จึงไม่รับ
จะลองใหม่เมื่อมี transposition table (ท่าจากตารางช่วยให้ท่าแรกถูกบ่อยขึ้น ซึ่งเป็นเงื่อนไขที่ทำให้ PVS ได้ผล)

### s5 (LMR) เทียบ s4 (`wyrd-iv` ทั้งสองฝั่ง)

| `Nodes` | เกม | Elo | ± | ผลตามกฎ |
|---:|---:|---:|---:|---|
| 1,000 | 2,000 | +2 | 3 | ไม่มีผล |
| 10,000 | 2,000 | +28 | 13 | ผ่าน (ขอบล่าง +15.5) |
| 50,000 | 2,000 | +23 | 14 | ผ่าน (ขอบล่าง +9.9) |

- ตัวเลขชุด 600 เกมแรกแกว่งและเฉียดเกณฑ์ (10k node: +15 ± 24 ไม่ผ่าน) จึงเพิ่มเป็น 2,000 เกมต่อระดับก่อนตัดสิน
- ลองสองค่าพารามิเตอร์ ชุด v0 (ดัชนี ≥ 3, ลด 2 เมื่อดัชนี ≥ 6 และ depth ≥ 6) ได้ +13 ± 13 ที่ 10k (ขอบล่าง +0.1) และ +29 ± 14 ที่ 50k
  ชุด v1 (ค่าที่ใช้จริง ตามแถว s5 ด้านบน) ได้ผลดีกว่าที่ 10k จึงเลือก v1 การเลือกค่าจากข้อมูลชุดเดียวกับที่ใช้ตัดสิน มีความเสี่ยงที่ผลจะดูดีเกินจริงเล็กน้อย
- **ต้นทุนความเร็ว:** ต่อ node ช้าลง ~13% (3,000,000 node: ~790 ms เทียบ ~695 ms ของ s4) ตัวเลข Elo ข้างบนเป็นที่ node เท่ากัน
  ที่เวลาเท่ากัน ผลสุทธิจะน้อยกว่านี้ ยังไม่ได้วัดเพราะ engine ยังจำกัดด้วย node ไม่ใช่เวลา ต้องวัดเมื่อทำเฟิร์มแวร์
- สัมประสิทธิ์รีดักชันเป็นค่าคงที่ที่ลองเอง ไม่ได้ปรับอย่างเป็นระบบ

### s6 (transposition table 64 KB) เทียบ s5 (`wyrd-iv` ทั้งสองฝั่ง)

| `Nodes` | เกม | Elo | ± | ผลตามกฎ |
|---:|---:|---:|---:|---|
| 1,000 | 600 | −1 | 11 | ไม่มีผล |
| 10,000 | 2,000 | +52 | 14 | ผ่าน (ขอบล่าง +38.5) |
| 50,000 | 2,000 | +125 | 15 | ผ่าน (ขอบล่าง +110.5) |

- ต่อ node ความเร็วไม่ต่างจาก s5 (3,000,000 node: ~790–850 ms ทั้งคู่ ในค่าคลาดเคลื่อนของการจับเวลา)
- **ขนาดตาราง** (เทียบ 64 KB ที่ 50,000 node, 600 เกมต่อขนาด): 16 KB −22 ± 21, 256 KB +8 ± 14, 4 MB +6 ± 14
  แปลว่า 64 KB ได้ผลเกือบเต็มที่ในช่วง node ที่วัด การเพิ่มเป็น 256 KB หรือ 4 MB ไม่ต่างจากศูนย์อย่างมีนัยสำคัญ
  ส่วน 16 KB ลดลง (ไม่ผ่านเกณฑ์ ขอบ ± กว้างกว่าส่วนต่าง ยืนยันได้แค่ทิศทาง) ที่ node สูงกว่านี้ตารางใหญ่อาจมีประโยชน์ ยังไม่ได้วัด
- ตั้งขนาดได้ผ่าน UCI `Hash` (หน่วย KiB, 0 = ปิด) หรือ `Searcher::with_tt_kb`; ค่าเริ่มต้น 64 KB (`DEFAULT_TT_KB`)
- **หน่วยความจำ:** 64 KB (ตารางจำ) บวก 16 KB (history) ต้องนับในงบ RAM ของ ESP32 (520 KB ทั้งหมด รวม net 49 KB)
- **ข้อจำกัดที่ทราบ:**
  - ตารางถูกสร้างใหม่ทุกครั้งที่สั่ง `go` (ไม่ข้ามตา) ผลจึงมาจากการใช้ซ้ำภายในการค้นหาครั้งเดียว (iterative deepening) เท่านั้น
    การเก็บตารางข้ามตาน่าจะได้เพิ่มอีก ยังไม่ได้ทำ
  - ผลเสมอจากการเดินซ้ำ (ข้อ s2) ขึ้นกับเส้นทาง แต่ถูกเก็บในตาราง อาจให้คะแนนผิดในบางตำแหน่ง เป็นข้อบกพร่องที่ยอมรับกันทั่วไป ยังไม่ได้วัดผลกระทบ
  - ช่องตรวจ 16 บิตทำให้ชนกันผิดตำแหน่งได้นาน ๆ ครั้ง
  - `datagen` และเว็บเดโมเรียก `Searcher::new` เหมือนเดิม จึงได้ตาราง 64 KB อัตโนมัติ ข้อมูลเทรนรอบถัดไปจะต่างจากรอบก่อน (ต้องบันทึก commit ของ datagen ตามกฎเหล็กข้อ 1)
- PVS ลองไม่ผ่านใน s3 ตอนยังไม่มีตาราง ยังไม่ได้ลองซ้ำหลังมี s6
