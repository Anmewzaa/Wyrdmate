# การทดสอบความแรงและเกณฑ์รับ net

เอกสารนี้กำหนดขั้นตอนมาตรฐานในการตัดสินว่า net ใหม่ **แรงกว่า** net เดิมหรือไม่
ซึ่งเป็นเงื่อนไขบังคับก่อนนำ net เข้า `nets/` (กฎเหล็กข้อ 2 ใน `CLAUDE.md`)

## 1. หลักการ

- ค่า loss ที่ต่ำลงไม่เป็นหลักฐานว่าเล่นเก่งขึ้น (net อาจจำข้อมูลได้ หรือข้อมูลเปลี่ยนไป
  ทำให้ loss เปรียบเทียบข้ามชุดข้อมูลไม่ได้)
- ตัวตัดสินคือ **ผลการแข่งจริง** ระหว่าง engine ที่ใช้ net ใหม่กับ engine ที่ใช้ net เดิม
- ผลต้องเกินช่วงความคลาดเคลื่อน (ขอบล่างของช่วง ± ต้องมากกว่า 0)
- รายงานผลตามจริง รวมถึงการทดลองที่ไม่ผ่าน (กฎเหล็กข้อ 7)

## 2. เครื่องมือ

| เครื่องมือ | หมายเหตุ |
|---|---|
| `fastchess` v1.8.3-alpha | ไม่อยู่ใน repository ดาวน์โหลด `fastchess-windows-x86-64.zip` จาก [releases](https://github.com/Disservin/fastchess/releases) |
| ชุดตำแหน่งเปิดเกม | สร้างด้วย `engine/examples/book.rs` |
| ไบนารี engine | `cargo build --release -p wyrdmate-engine` |

## 3. ขั้นตอน

### 3.1 สร้างชุดตำแหน่งเปิดเกม

```bash
cargo run --release -p wyrdmate-engine --example book -- 300 99 data/book.epd
```

ได้ 300 ตำแหน่งเปิดเกมแบบสุ่มที่สมดุล (seed 99) ใช้ชุดเดียวกันทุกการแข่งเพื่อให้เปรียบเทียบกันได้

### 3.2 รันการแข่ง

รันจาก PowerShell:

```text
fastchess -engine name=new cmd=<engine.exe> option.EvalFile=<quantised.bin> -engine name=old cmd=<engine.exe>
  -each proto=uci tc=inf nodes=10000 option.Nodes=10000 -openings file=data/book.epd format=epd order=random
  -rounds 300 -games 2 -repeat -concurrency 4 -maxmoves 120
  -draw movenumber=30 movecount=8 score=10 -resign movecount=4 score=800
```

| พารามิเตอร์ | ความหมาย |
|---|---|
| `nodes=10000`, `option.Nodes=10000` | จำกัดทั้งสองฝ่ายที่ 10,000 node ต่อตา (ไม่ใช้เวลาเป็นตัวจำกัด เพื่อให้ผลไม่ขึ้นกับเครื่อง) |
| `-rounds 300 -games 2 -repeat` | 300 ตำแหน่ง × 2 เกม (สลับสี) = **600 เกม** |
| `-maxmoves 120` | ตัดสินเสมอเมื่อครบ 120 ตา |
| `-draw ...` | ตัดสินเสมอเมื่อคะแนนใกล้ 0 นานพอ |
| `-resign ...` | ตัดสินแพ้เมื่อได้เปรียบเกิน 800 เซนติเบี้ย 4 ตาติดกัน |

เมื่อเทียบกับ engine นับมูลค่าหมาก ให้ฝั่ง `old` ไม่ใส่ `option.EvalFile`

### 3.2.1 สคริปต์ที่รันให้

`scripts/ab.ps1` ทำขั้นตอนข้อ 3.2 ให้ครบ: build engine รุ่นใหม่/เก่าจาก git ref (เก็บไบนารีไว้ที่ `tools/engines/`),
สร้างชุดตำแหน่งเปิดถ้ายังไม่มี, แข่งด้วย fastchess และพิมพ์ผล พร้อมบรรทัด `VERDICT` ตามกฎ (ขอบล่างของ Elo ต้องมากกว่า 0)

```powershell
powershell -File scripts/ab.ps1                      # โค้ดที่ยังไม่ commit เทียบกับ HEAD
powershell -File scripts/ab.ps1 -New HEAD -Old c81e99b
powershell -File scripts/ab.ps1 -Net nets/wyrd-v.bin -OldNet nets/wyrd-iv.bin   # net เทียบ net (engine ตัวเดียวกัน)
```

บันทึกผลที่ `logs/ab-<ชื่อ>.txt` และ `.pgn` (git-ignored) พารามิเตอร์: `-Nodes` (ค่าเริ่มต้น 10,000), `-Rounds` (300 = 600 เกม),
`-Concurrency`, `-Tag` (ตั้งชื่อไฟล์ผล) ต้องมี `tools/fastchess` ตามที่ระบุใน CLAUDE.md

### 3.3 ตรวจความถูกต้องของการอ่าน net (ก่อนแข่ง)

```bash
cargo run --release -p wyrdmate-engine --example validate -- <net.bin> <data.txt>
```

ค่าสหสัมพันธ์ประมาณ 0.83 หมายความว่า engine อ่าน net ได้ตรงกับ trainer
หากต่ำผิดปกติ แสดงว่ามีความไม่ตรงกันของโครงสร้างหรือการแมปฟีเจอร์ ให้แก้ก่อนแข่ง

## 4. เกณฑ์การรับ net

net ใหม่จะถูกรับก็ต่อเมื่อครบทุกข้อ:

1. แข่งกับ net ปัจจุบัน อย่างน้อยหลายร้อยเกม (ที่ผ่านมาใช้ 600 เกม)
2. Elo ที่วัดได้ **ขอบล่างของช่วงความคลาดเคลื่อนมากกว่า 0**
3. มีบันทึกที่มาครบใน `nets/RECORDS.md` (ดูข้อ 5)
4. เพิ่มแถวผลแข่งใน `docs/progress/data.json` และสร้างกราฟใหม่

## 5. ข้อมูลที่ต้องบันทึก

ใน `nets/RECORDS.md` (กฎเหล็กข้อ 1):

- git commit ของเครื่องมือที่ใช้ และ rev ของ bullet
- อาร์กิวเมนต์ของ `wyrdmate-trainer` ทั้งหมด
- ข้อมูลเทรน: seed, nodes, จำนวนเกม, net ที่ใช้เล่นสร้างข้อมูล, จำนวนตำแหน่ง
- ผลแข่ง: คู่แข่ง, จำนวนเกม, Elo ± ความคลาดเคลื่อน

ใน `docs/progress/data.json`: เพิ่มแถวใน `matches` ทุกครั้งที่แข่งเสร็จ
(`net, vs, elo, err, games, accepted, finished, commit`) และเพิ่มชุดข้อมูลใน `loss` เมื่อการเทรนนั้นควรเก็บไว้
จากนั้นสร้างกราฟใหม่:

```text
powershell -File scripts/make-progress-svg.ps1
```

- ขั้นต่ำสุดของ `UCI_Elo` คือ 1320 ระดับต่ำกว่านั้นของเราอ่านค่าเฉพาะไม่ได้
- ได้คะแนนเท่ากันในสองคู่ (6,400 กับ 12,800; 1,600 กับ 3,200) ตรงกับตารางข้อ 8 ยังไม่ทราบสาเหตุ
  (เบาะแสสำหรับงานปรับปรุง search ใน ROADMAP)
- วัดบน search รุ่นปัจจุบันเท่านั้น หากเปลี่ยน search ต้องวัดซ้ำ

### PVS ลองซ้ำหลังมีตารางจำ: ยังไม่รับ

เทียบ s6 (600 เกมต่อระดับ, `wyrd-iv` ทั้งสองฝั่ง, ใช้ร่วมกับ LMR และ null-move): 1,000 node **−36 ± 23**, 10,000 node **−10 ± 22**, 50,000 node **−1 ± 25**

- สมมติฐานเดิมว่า "ตารางทำให้ท่าแรกถูกบ่อยขึ้น PVS จึงได้ผล" ไม่ได้รับการยืนยัน
- วัดคร่าว ๆ ด้วย 3 ตำแหน่ง ครั้งละหนึ่งการค้นหา (ตัวนับชั่วคราว ไม่ได้เก็บไว้ในโค้ด): สัดส่วนโหนดที่ตัดกิ่งได้ด้วยท่าแรก

  ค่าที่เข้ากับ PVS ได้ผลมักอยู่ที่ราว 85–95% ตัวเลขนี้เป็นเบาะแสที่สอดคล้องกับผล แต่เป็นตัวอย่างเล็กมาก ไม่ใช่ข้อพิสูจน์
