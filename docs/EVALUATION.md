## 1. หลักการ

- **loss ที่ต่ำลงไม่ใช่หลักฐานว่าเล่นเก่งขึ้น** (net อาจจำข้อมูลได้ หรือข้อมูลเปลี่ยนจนเปรียบเทียบ loss ข้ามชุดข้อมูลไม่ได้)
- ตัวตัดสินคือ **ผลแข่งจริง (A/B match)** ระหว่าง engine รุ่นใหม่กับรุ่นเดิมที่ node limit เท่ากัน
- ผลต้องเกิน error bar: **ขอบล่างของ Elo ± ต้องมากกว่า 0**
- รายงานผลตามจริง รวมถึงการทดลองที่ไม่ผ่าน (กฎเหล็กข้อ 7)

## 3. ขั้นตอน A/B match

### 3.1 Opening book

```bash
cargo run --release -p wyrdmate-engine --example book -- 300 99 data/book.epd
```

ได้ 300 ตำแหน่งเปิดเกมสุ่มที่สมดุล (seed 99) ใช้ชุดเดียวกันทุกการแข่งเพื่อเปรียบเทียบกันได้

> **ข้อควรระวัง: opening ซ้ำ.** engine จำกัด node เล่นซ้ำได้ผลเหมือนเดิมทุกครั้ง ถ้าสั่ง `-rounds` มากกว่าจำนวนตำแหน่งในชุด (300) เกมจะซ้ำกันเอง
> Elo ที่ได้เท่าเดิมแต่ error bar แคบลงเกินจริง การเพิ่มเกมต้องใช้ชุด opening **อื่น** (seed อื่น ด้วย `-Book data\book2.epd`) แล้วรวมผลของชุดอิสระ
> `ab.ps1` เตือนเมื่อ `-Rounds` เกินขนาดชุด

### 3.2 สคริปต์ `scripts/ab.ps1`

build engine รุ่นใหม่/เก่าจาก git ref (เก็บไบนารีที่ `tools/engines/`) แข่งด้วย fastchess และพิมพ์ผลพร้อมบรรทัด `VERDICT` ตามกฎ

```powershell
powershell -File scripts/ab.ps1                                    # โค้ดที่ยังไม่ commit เทียบกับ HEAD
powershell -File scripts/ab.ps1 -New HEAD -Old c81e99b             # search รุ่นใหม่ เทียบรุ่นเก่า
powershell -File scripts/ab.ps1 -Net nets/wyrd-vi.bin -OldNet nets/wyrd-v.bin   # net เทียบ net (engine ตัวเดียวกัน)
```

| พารามิเตอร์ | ความหมาย |
|---|---|
| `-Nodes` | node limit ต่อ move ของทั้งสองฝั่ง (ค่าเริ่มต้น 10,000) |
| `-NewNodes` | node limit ของฝั่งใหม่เท่านั้น ใช้เทียบที่ "เวลาเท่ากัน" (ข้อ 7.2) |
| `-Rounds` | 300 = 600 เกม (300 opening × 2 เกมสลับสี) |
| `-Book` | opening book (ค่าเริ่มต้น `data\book.epd`) |
| `-Concurrency`, `-Tag` | จำนวนเกมพร้อมกัน, ชื่อไฟล์ผล |
| `-NewHash` | ขนาด TT (KiB) ของฝั่งใหม่เท่านั้น |

ผลบันทึกที่ `logs/ab-<ชื่อ>.txt`, `.pgn` และ `.meta.json` (ชื่อ net ที่แข่งกัน ให้ `monitor.py` อ่าน) ทั้งหมดอยู่ใน `.gitignore`

คำสั่ง fastchess ที่สคริปต์รัน (ถ้าต้องการรันเอง):

```text
fastchess -engine name=new cmd=<engine.exe> option.EvalFile=<net> option.Nodes=10000 nodes=10000
          -engine name=old cmd=<engine.exe> option.EvalFile=<net> option.Nodes=10000 nodes=10000
  -each proto=uci tc=inf -openings file=data/book.epd format=epd order=random
  -rounds 300 -games 2 -repeat -concurrency 4 -maxmoves 120
  -draw movenumber=30 movecount=8 score=10 -resign movecount=4 score=800
```

`-maxmoves 120` ตัดสินเสมอเมื่อครบ 120 ตา, `-draw` เสมอเมื่อคะแนนใกล้ 0 นานพอ, `-resign` แพ้เมื่อเสียเปรียบเกิน 800 cp 4 ตาติด
เมื่อเทียบกับ material eval ให้ฝั่ง `old` ไม่ใส่ `option.EvalFile` (`-OldNet material`)

### 3.3 ตรวจการอ่าน net ก่อนแข่ง

```bash
cargo run --release -p wyrdmate-engine --example validate -- <net.bin> <data.txt>
```

ค่า correlation ประมาณ 0.83 หมายความว่า engine อ่าน net ตรงกับ trainer ถ้าต่ำผิดปกติ แสดงว่าโครงสร้างหรือการแมป feature ไม่ตรงกัน ให้แก้ก่อนแข่ง

## 4. เกณฑ์รับและข้อมูลที่ต้องบันทึก

net หรือ search รุ่นใหม่ถูกรับก็ต่อเมื่อครบทุกข้อ:

1. แข่งกับรุ่นปัจจุบันอย่างน้อยหลายร้อยเกม (ที่ผ่านมา 600 เกม ต่อระดับ node)
2. ขอบล่างของ Elo มากกว่า 0
3. มีบันทึกที่มาครบ: net ใน `nets/RECORDS.md`, search ในข้อ 7 ของเอกสารนี้
4. เพิ่มแถวผลแข่งใน `docs/progress/data.json` และสร้างกราฟใหม่ (`powershell -File scripts/make-progress-svg.ps1`)

**net:** บันทึกใน `nets/RECORDS.md` (กฎเหล็กข้อ 1): git commit ของเครื่องมือและ rev ของ bullet, อาร์กิวเมนต์ของ `wyrdmate-trainer` ทั้งหมด,
ข้อมูลเทรน (seed, nodes, จำนวนเกม, net ที่ใช้เล่น, จำนวนตำแหน่ง) และผลแข่ง (คู่แข่ง, จำนวนเกม, Elo ± error bar)

**data.json:** เพิ่มแถวใน `matches` ทุกครั้งที่แข่งเสร็จ (`net, vs, elo, err, games, accepted, finished, commit`) และเพิ่มชุดข้อมูลใน `loss` เมื่อการเทรนนั้นควรเก็บไว้

เมื่อผลที่ระดับ node หนึ่งผ่านแต่อีกระดับไม่ผ่าน (เช่น `r7a`: ผ่านที่ 10k ไม่ผ่านที่ 50k) ให้เพิ่มเกมด้วย opening book ชุดอื่นก่อนตัดสิน
และผู้ดูแลโครงการเป็นคนตัดสินรับหรือไม่รับ ผลที่ไม่ได้รับยังบันทึกไว้

**ข้อควรระวังในการอ่าน:**

- Elo เป็น **ค่าสัมพัทธ์ภายในกลุ่มเดียวกัน** (1,600 node ของรุ่นนั้น = 0) ไม่ใช่ Elo สัมบูรณ์ **ข้ามคอลัมน์เทียบความแรงตรง ๆ ไม่ได้**
  (เช่น ตัวเลขต่อ node ที่สูงขึ้นไม่ได้แปลว่า 1,600 node ของ s9 แรงกว่า s6)
- ระดับต่ำ ๆ (100–200 node) คะแนนต่ำมาก (4–9%) ค่า ± ไม่น่าเชื่อถือ ใน s9 100 node ติดพื้นถึง −845
- ช่วง 6,400 → 12,800 node ที่เคยต่างกันเพียง ~33 Elo ใน s9 หายไปใน s10 (ต่างกัน 108) ส่วนช่วง 200 → 400 node ต่างกันถึง 224 ผิดปกติ ยังไม่ทราบสาเหตุ ระดับ node ต่ำเสียเปรียบจาก SEE ที่ตัด capture ตอน search ยังตื้นมาก (สมมติฐาน ไม่ได้ทดสอบ)
- วัดที่ node ต่อ move คงที่ ไม่ใช่เวลา ความเร็วต่อ node บนบอร์ดจะต่างจากพีซี

**ข้อจำกัดของตัวเลขนี้ (ต้องระบุเมื่ออ้างอิง):**

- error รวมของ `UCI_Elo` ที่แปลงแล้วราว ±80–100 และเป็นค่าประมาณ ไม่ใช่ Elo มาตรฐาน (CCRL/FIDE)
- `UCI_Elo` ปรับเทียบที่ time control ยาวกว่านี้มาก และเป็นการ "ทำให้อ่อนลงโดยตั้งใจ" ไม่ใช่ engine ที่อ่อนจริง มาตราจึงถูกบีบ (ตั้งห่าง 200 แต่วัดได้ราว 62–157)
  ช่วง 1320→1500 ที่ใช้แปลงใกล้ค่าที่ตั้ง ยิ่งไกลจากช่วงนี้ยิ่งไม่แม่น
- ขั้นต่ำสุดของ `UCI_Elo` คือ 1320 ระดับต่ำกว่านั้นของเราอ่านค่าเฉพาะไม่ได้
- สรุป (ที่ s6): 51,200 node เล่นระดับผู้เล่นสมัครเล่นตามมาตรานี้ ราว Stockfish 1500–1550 และการเพิ่ม node เกิน 12,800 ยังเพิ่มความแรงต่อเนื่อง เพดานจริงอยู่สูงกว่า 51,200 (ยังไม่ได้วัดที่ node สูงกว่านี้)

## 7. ผล A/B ของ search

search ใช้เกณฑ์เดียวกับ net: แข่งที่ node เท่ากัน 600 เกมต่อระดับกับรุ่นก่อน (`wyrd-iv` ทั้งสองฝั่ง ยกเว้นข้อ 7.2 ใช้ `wyrd-vi`) ขอบล่างของ Elo ต้องมากกว่า 0
หลังเปลี่ยน search ตาราง ladder ต้องวัดซ้ำ (ทำแล้วกับ s10) ส่วน Stockfish ยังเป็นของ s6

**หมายเหตุรายรุ่น:**

- **s2:** ก่อนแก้ engine ไม่รู้จักการเดินซ้ำเลย (`cozy-chess` ไม่ตรวจให้) จึงเดินวนซ้ำตอนได้เปรียบและ fastchess ตัดสินเสมอซ้ำสามครั้งให้ ผลต่างมาจากการเลี่ยงเสมอที่ไม่จำเป็นเป็นหลัก
  ตรวจเฉพาะ "เคยเกิดมาหนึ่งครั้ง" ยังไม่ตรวจเสมอเพราะหมากไม่พอ `datagen` ไม่ส่งประวัติเกม และเว็บเดโมส่งแค่ FEN จึงเห็น repetition เฉพาะภายใน search
- **s3:** แก้เฉพาะการจัดลำดับ move ดีสุดที่รากได้ +15 ± 20 (ไม่ผ่านเมื่อวัดเดี่ยว ๆ) จึงรับพร้อม killer/history เป็นชุดเดียว
  หลังเปลี่ยนเป็น `sort_by_cached_key` ความเร็วเท่า s2 (ก่อนหน้านั้นช้ากว่า ~23%) หน่วยความจำเพิ่ม 16 KB (history) + killer
- **s4:** ลอง R=3 เมื่อ depth ≥ 6 แล้วผลเท่า R=2 จึงคง R=2 ผลที่ 10k เป็นหลักฐานอ่อน ที่ 50k แข็งแรงกว่า
- **s5:** ลองสองค่าพารามิเตอร์ (v0: index ≥ 3 ได้ +13 ± 13 ที่ 10k, v1 ที่ใช้จริงได้ดีกว่า) การเลือกค่าจากข้อมูลชุดเดียวกับที่ตัดสินเสี่ยงให้ผลดูดีเกินจริงเล็กน้อย
- **s6:** ขนาดตาราง (เทียบ 64 KB ที่ 50k, 600 เกมต่อขนาด): 16 KB −22 ± 21, 256 KB +8 ± 14, 4 MB +6 ± 14 แปลว่า 64 KB ได้ผลเกือบเต็ม
  ข้อจำกัด: ตารางสร้างใหม่ทุก `go` (ไม่ข้ามตา), ผลเสมอจากการเดินซ้ำขึ้นกับเส้นทางแต่ถูกเก็บในตาราง (ยังไม่ได้วัดผลกระทบ), key ตรวจ 16 บิตทำให้ชนกันได้นาน ๆ ครั้ง
- **s7, s8:** margin (150 ต่อ ply, 200) ลองครั้งเดียว ไม่ได้ปรับ
- **s9:** ยังไม่ขยายที่ move ระดับราก และยังไม่ได้ปรับเพดาน ply

**ความเร็วต่อ node** (`go` ที่ 3,000,000 node จาก 4 ตำแหน่ง เริ่มต้น/เปิด/กลางเกม/ปลายเกม จับเวลาทั้งโปรเซสบน Windows จึงมีสัญญาณรบกวน):
s5 ช้ากว่า s4 ~13% · s6 ไม่ต่างจาก s5 · s7 ช้ากว่า s6 ~12% · s8 ช้ากว่า s7 ~12% (ส่วนต่างมาจากตำแหน่งกลางเกมตำแหน่งเดียวเป็นหลัก น่าจะเป็นผลของการนับ node:

### 7.3 PVS: ลองแล้วไม่รับ

**ข้อจำกัด:** เทรนครั้งเดียวต่อขนาด (ยังไม่รู้ความผันผวนระหว่างการเทรนซ้ำ) เวลาเป็นเวลาบนพีซีขณะรัน 12 เกมพร้อมกัน บน ESP32 สัดส่วนต้นทุนของ net ต่อ search อาจต่างออกไป

ทิศทางเป็นบวกแต่ไม่พ้น error bar จึงไม่รับ ข้อมูลคุณภาพสูงขึ้นอาจช่วยเล็กน้อย แต่ไม่ใช่คอขวดใหญ่ (เทียบ `r7a` ที่ใช้ 5,000 node: +39 / +17 ที่ 10k / 50k ซึ่งไม่ได้ต่ำกว่า)
แข่ง `r7b` กับ `r7a` โดยตรง (600 เกม): 10,000 node **+34 ± 25** (ขอบล่าง +8) 50,000 node **−3 ± 24** (ขอบล่าง −28) เท่ากันที่ 50k จึงสรุปว่า node ต่อ move ที่สูงขึ้นไม่ได้ทำให้ net ดีขึ้นชัดเจน เทรนครั้งเดียว ยังไม่รู้ความผันผวนระหว่างการเทรนซ้ำ

## 9. ข้อจำกัดที่ต้องระบุเมื่อรายงานผล

- วัดเทียบกับรุ่นก่อนของโครงการเอง ส่วนเทียบ engine ภายนอกมีเพียง Stockfish จำกัดความแรง (ข้อ 6) ซึ่งเป็นค่าประมาณหยาบ **ยังไม่มี Elo สัมบูรณ์มาตรฐาน**
- ผลวัดที่ node limit คงที่ (ส่วนใหญ่ 10,000 และ 50,000) ที่ node อื่นผลอาจต่าง และ **ไม่ใช่เวลา** เวลาต่อ node บนบอร์ดจริงต่างจากพีซี
- opening book สร้างจาก seed เดียว (99) เป็นหลัก
- ตัวเลขที่รวมหลายชุดเกมเข้าด้วยกันโดยคำนวณเอง (เช่น `r7a` ที่ 50k) เป็นค่าประมาณแบบหยาบ ไม่ใช่ค่าที่ fastchess คำนวณ
