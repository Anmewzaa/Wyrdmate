## 1. ภาพรวม

การค้นหาคือการลองเดินล่วงหน้าหลายตาเป็นต้นไม้ แล้วเลือกตาแรกที่นำไปสู่ผลดีที่สุด
โดยสมมติว่าคู่ต่อสู้เล่นดีที่สุดเช่นกัน เทคนิคทั้งสี่ทำงานซ้อนกันดังนี้

```text
search            วนค้นความลึก 1, 2, 3, ... (iterative deepening)
 └─ negamax       ค้นแบบมินิแมกซ์ที่ความลึกที่กำหนด
     │             └─ alpha-beta ตัดกิ่งที่ไม่มีวันถูกเลือก
     └─ (ความลึกหมด)
         quiesce  ค้นต่อเฉพาะการกินและการโปรโมตจนสงบ แล้วประเมินด้วย NNUE
```

| เทคนิค | หน้าที่ | ฟังก์ชัน |
|---|---|---|
| Iterative deepening | ค้นทีละความลึก ให้มีคำตอบใช้ได้เสมอ | `Searcher::search` |
| Negamax | ค้นต้นไม้ตาเดินสำหรับทั้งสองฝ่ายด้วยฟังก์ชันเดียว | `negamax` |
| Alpha-beta | ตัดกิ่งโดยไม่เปลี่ยนผลลัพธ์ | ภายใน `negamax` และ `quiesce` |
| Quiescence | หลีกเลี่ยงการประเมินกลางการแลกหมาก | `quiesce` |

คะแนนทุกค่าเป็นเซนติเบี้ยจากมุมมองของฝ่ายที่ถึงตา

## 2. Iterative deepening

`Searcher::search(&board, max_depth)` ค้นความลึก 1, 2, 3, ... จนถึง `max_depth` หรือจนหมด node

แต่ละรอบ:

1. เรียงตาเดินที่ราก (ตำแหน่งปัจจุบัน) ตามข้อ 6
2. ลองทีละตาด้วย `negamax` ที่ความลึก `depth - 1` เก็บตาที่ได้คะแนนสูงสุด
3. ถ้าไม่ถูกขัดจังหวะ ใช้ผลรอบนี้เป็นคำตอบ และย้ายตาที่ดีที่สุดไว้หน้าสุดสำหรับรอบถัดไป

ประโยชน์สองประการ:

- **มีคำตอบเสมอ:** หาก node หมดกลางรอบ จะทิ้งผลของรอบที่ยังไม่เสร็จ และคืนผลของความลึกล่าสุดที่เสร็จสมบูรณ์
- **ตัดกิ่งได้มากขึ้น:** ตาที่ดีที่สุดของรอบก่อนมักยังดีที่สุดในรอบลึกกว่า การลองก่อนช่วยให้ alpha-beta ตัดได้มาก

หากไม่มีตาเดินที่ถูกกติกา (`legal_moves` ว่าง) คืนค่า `None`

## 3. Negamax

มินิแมกซ์ปกติ: ฝ่ายเราเลือกตาที่ให้คะแนนสูงสุด ฝ่ายตรงข้ามเลือกตาที่ให้คะแนนเราต่ำสุด
negamax อาศัยข้อเท็จจริงว่า **คะแนนของฝ่ายหนึ่งเท่ากับค่าติดลบของคะแนนอีกฝ่าย**
จึงเขียนฟังก์ชันเดียวสำหรับทั้งสองฝ่ายได้ ในโค้ดคือ

```rust
let score = -self.negamax(&next, depth - 1, -beta, -alpha, ply + 1);
```

ขั้นตอนของแต่ละ node ใน `negamax`:

1. **ตรวจจบเกม:** รุกฆาตคืน `-MATE + ply` (ยิ่งรุกฆาตเร็ว `ply` ยิ่งน้อย จึงยิ่งดีสำหรับฝ่ายที่รุกฆาต) เสมอคืน 0
2. **ความลึกหมด** (`depth <= 0`): ส่งต่อให้ `quiesce`
3. **นับ node** (`tick`): หากถึง `node_limit` ตั้งธง `stopped` แล้วหยุด
4. **สร้างตาเดิน** ทั้งหมด เรียงลำดับ ลองทีละตาแล้วเก็บคะแนนที่ดีที่สุด

## 4. Alpha-beta

ระหว่างค้นหาเก็บสองค่า:

| ค่า | ความหมาย |
|---|---|
| `alpha` | คะแนนที่ดีที่สุดที่ฝ่ายถึงตาการันตีได้แล้ว |
| `beta` | คะแนนสูงสุดที่ฝ่ายตรงข้ามยอมให้ฝ่ายถึงตาได้ |

หากพบตาเดินที่ให้คะแนน `>= beta` (ในโค้ด `if alpha >= beta { break; }`) แปลว่าฝ่ายตรงข้าม
จะไม่ยอมให้เกิดตำแหน่งนี้ตั้งแต่ตาก่อนหน้า จึงไม่ต้องลองตาเดินที่เหลือใน node นี้

**ตัวอย่าง:** ตาเดินที่ลองไปแล้วการันตีได้ +100 ตอนนี้ลองตาเดินอีกทางหนึ่ง
หากพบว่าคู่ต่อสู้มีคำตอบเดียวที่ทำให้เหลือ −300 ก็ไม่ต้องหาต่อว่าคำตอบอื่นเป็นอย่างไร
เพราะทางนี้แย่กว่า +100 แน่นอน

ผลลัพธ์ **เหมือนมินิแมกซ์เต็มรูปแบบทุกประการ** แต่ค้นน้อยลงมาก
ยิ่งลองตาที่ดีก่อนเท่าใด การตัดกิ่งยิ่งได้มาก (ดูข้อ 6)

## 5. Quiescence search

**ปัญหา:** หากหยุดค้นที่ความลึกคงที่แล้วประเมินทันที อาจหยุดกลางการแลกหมาก
เช่นเพิ่งกินม้า แต่อีกฝ่ายกินกลับได้ในตาถัดไป คะแนนในขณะนั้นจึงคลาดเคลื่อนมาก
(เรียกว่า horizon effect)

`quiesce` แก้ปัญหาโดยเมื่อความลึกหมด จะยังไม่ประเมินทันที แต่:

1. คำนวณ `stand` คือคะแนนของตำแหน่งนี้ด้วย NNUE (หรือ eval แบบนับมูลค่าหมากหากไม่มี net)
   ซึ่งหมายถึงคะแนนหากฝ่ายที่ถึงตา "ไม่กินอะไรต่อ" และใช้เป็นขอบล่างของ node นี้
2. หาก `stand >= beta` ตัดกิ่งทันที
3. ปรับ `alpha` ให้ไม่ต่ำกว่า `stand`
4. ลองเฉพาะ **ตาเดินที่เป็นการกินหรือการโปรโมต** แล้วเรียก `quiesce` ซ้ำ
5. ทำต่อจนไม่มีการกินเหลือ ตำแหน่งนั้นจึงถือว่า "สงบ"

ดังนั้นการประเมินด้วย NNUE เกิดกับตำแหน่งที่ไม่ได้อยู่กลางการแลกหมากเป็นหลัก
ซึ่งสอดคล้องกับ datagen ที่เก็บเฉพาะตำแหน่งสงบ

> **จุดที่เกี่ยวข้องกับประสิทธิภาพ:** การประเมินเกิดที่ `quiesce` ทุกครั้ง
> accumulator ของ NNUE อัปเดตแบบ incremental ต่อหนึ่งตา ดู [ROADMAP.md](ROADMAP.md) ข้อ 4

## 6. การเรียงตาเดิน

ฟังก์ชัน `move_score` ให้คะแนนเพื่อเรียงตาเดินจากมากไปน้อยก่อนลอง (คำนวณครั้งเดียวต่อท่าด้วย `sort_by_cached_key`):

| ลำดับ | ชนิดตาเดิน | คะแนนเรียง |
|---|---|---:|
| 1 | ท่าที่เก็บในตารางจำ (ท่าดีสุดที่เคยพบในตำแหน่งนี้) | 30,000 |
| 2 | กินหมาก | `10,000 + 10 × มูลค่าหมากที่ถูกกิน − มูลค่าหมากที่กิน` (MVV-LVA: กินของแพงด้วยของถูกก่อน) |
| 3 | โปรโมต | `+9,000` |
| 4 | killer move ตัวที่ 1 / 2 ของระยะ ply นั้น | 8,000 / 7,000 |
| 5 | ท่าเงียบอื่น ๆ | ค่า history ÷ 8 (ติดลบได้) |

- **killer moves:** ท่าเงียบ 2 ท่าต่อ ply ที่เพิ่งทำให้ตัดกิ่ง (beta cutoff) ได้ในพี่น้องของมัน
- **history heuristic:** ตาราง `[ฝ่าย][จาก][ไป]` ของ `i16` (16 KB) ท่าที่ทำให้ตัดกิ่งได้รับโบนัสตามความลึก² (สูงสุด 400)
  ท่าเงียบที่ลองก่อนหน้าแล้วไม่ตัดถูกหักคะแนน ใช้สูตรถ่วง (gravity) ไม่ให้ค่าเกิน ±16,384
- **ที่ราก:** ท่าดีสุดของรอบ iterative deepening ก่อนหน้าไปก่อน ท่าอื่นคงลำดับเดิม
  (โค้ดเดิมเรียงใหม่ด้วยคะแนนคงที่ทุกรอบ ทำให้ท่าดีสุดถูกสลับกลับ แก้แล้วใน s3)

มูลค่าหมากที่ใช้เรียง: เบี้ย 100, ม้า 320, บิชอป 330, เรือ 500, ควีน 900, คิง 0

ข้อสังเกตจากโค้ด: `is_capture` ตรวจว่าช่องปลายทางมีหมากฝ่ายตรงข้ามอยู่ จึง **ไม่นับ en passant**
เป็นการกิน (ช่องปลายทางว่าง) ผลคือ en passant ไม่ถูกลองใน `quiesce` และเรียงเป็นตาเดินธรรมดาใน `negamax`
ยังไม่ได้ทดสอบว่ามีผลต่อความแรงหรือไม่ และไม่กระทบความถูกต้องของตาเดิน
เพราะ `legal_moves` ยังสร้างตานี้ตามกติกา

## 7. เทคนิคตัดกิ่งและจำผล

ทั้งหมดอยู่ใน `negamax_node` ผลที่วัดได้ของแต่ละอย่างอยู่ใน [EVALUATION.md](EVALUATION.md) ข้อ 10

- **ตรวจการเดินซ้ำ (s2):** `Searcher` เก็บแฮชของตำแหน่งที่เล่นมา (ประวัติเกมจาก UCI `position ... moves` บวกเส้นทางที่ค้นอยู่)
  ตำแหน่งที่เคยเกิดมาแล้วหนึ่งครั้งภายในช่วงที่ halfmove clock อนุญาต นับเป็นเสมอ (0) ก่อนหน้านี้ engine ไม่รู้จักเลย
- **null-move pruning (s4):** ถ้า "ข้ามตา" แล้วค้นตื้นลง (R=2) ยังได้คะแนนถึง beta ก็ตัดกิ่งเลย ใช้เมื่อ depth ≥ 3,
  ไม่ถูกรุก, มีหมากที่ไม่ใช่เบี้ย/คิง (กัน zugzwang), beta ไม่ใช่คะแนนรุกฆาต, และไม่ทำซ้อนสองครั้งติด
- **late move reductions (s5):** ท่าเงียบที่ไม่ใช่ killer และไม่ให้รุก ตั้งแต่ท่าที่ 3 ในลำดับ (ดัชนี ≥ 2) ที่ depth ≥ 3 ค้นตื้นลง 1 ชั้น
  (2 ชั้นเมื่อดัชนี ≥ 5 และ depth ≥ 5) ถ้าได้คะแนนเกิน alpha ค่อยค้นซ้ำเต็มความลึก
- **transposition table (s6):** ตารางจำ 64 KB (ปรับด้วย UCI `Hash` เป็น KiB, 0 = ปิด) ช่องละ 8 ไบต์ bucket ละ 2 ช่อง
  เก็บคีย์ตรวจ 16 บิต, ท่าดีสุด, คะแนน (คะแนนรุกฆาตเก็บแบบสัมพัทธ์กับโหนด), ความลึก, ชนิดขอบเขต (แน่นอน/ขอบล่าง/ขอบบน)
  ใช้ตัดกิ่งเมื่อความลึกที่เก็บพอ และใช้ท่าที่เก็บเป็นท่าแรก ตารางถูกสร้างใหม่ทุกครั้งที่สั่ง `go` (ไม่ข้ามตา)

ลองแล้วไม่รับ: **PVS** (ลอง 2 ครั้ง ก่อนและหลังมีตารางจำ ไม่ผ่านกฎทั้งคู่)

## 8. การคุมความแรง

ความแรงควบคุมด้วย `node_limit` (กฎเหล็กข้อ 6 ใน `CLAUDE.md`):

- `Searcher::new(node_limit)` ทุกครั้งที่เข้า `negamax` (ที่ความลึกยังเหลือ) หรือ `quiesce` นับเป็นหนึ่ง node
- เมื่อถึงขีดจำกัด การค้นหาหยุด และ iterative deepening คืนผลของความลึกที่เสร็จล่าสุด
- node น้อย → ค้นลึกได้น้อย → เล่นอ่อนลง โดย net เดิม
- ตั้งผ่าน UCI ได้ด้วย `setoption name Nodes value N` (ค่าตั้งต้น 20,000) หรือ `go nodes N` สำหรับตาเดียว

ค่า node แต่ละระดับเทียบกับ Elo สัมพัทธ์แล้ว ดู [EVALUATION.md](EVALUATION.md) ข้อ 8 (วัดด้วย search รุ่นแรก) และข้อ 9 (เทียบ Stockfish)
ข้อ 8 และ 9 ในเอกสารนั้นเป็นของ search s1 ส่วนข้อ 8.1 และ 9.1 เป็นผลซ้ำด้วย search s6 (ที่ 51,200 node ได้ราว Stockfish 1530 จากเดิม ~1415)

## 9. ประวัติรุ่นของ search (s1 ถึง s6)

Elo เป็นผลแมตช์ A/B ที่จำนวน node เท่ากัน เทียบกับรุ่นก่อนหน้า (`wyrd-iv` ทั้งสองฝั่ง) ดูจำนวนเกมและรายละเอียดใน [EVALUATION.md](EVALUATION.md) ข้อ 10
เวลาคือเวลาที่ใช้ค้น 3,000,000 node บนเครื่องพัฒนา (ยิ่งน้อยยิ่งเร็วต่อ node) ค่าจับเวลาคลาดเคลื่อนราว ±5%

| รุ่น | เพิ่มอะไร | Elo ที่ 10k node | Elo ที่ 50k node | เวลา 3M node | RAM ที่เพิ่ม |
|---|---|---:|---:|---|---|
| s1 | negamax + alpha-beta + quiescence + iterative deepening | (ฐาน) | (ฐาน) | ~660–700 ms | |
| s2 | ตรวจการเดินซ้ำ | +44 | ไม่ได้วัด | ~660–680 ms | เล็กน้อย (แฮชของเส้นทาง) |
| s3 | killer + history + ท่าดีสุดที่ราก | +79 | +92 | ~660–700 ms (ครั้งแรกช้ากว่า ~23% จนแก้การเรียง) | ~17 KB |
| s4 | null-move pruning | +20 | +44 | ไม่ได้จับแยก | 0 |
| s5 | late move reductions | +28 | +23 | ~790 ms (ช้าลง ~13%) | 0 |
| s6 | transposition table 64 KB | +52 | +125 | ~820–850 ms (ไม่ต่างจาก s5) | 64 KB |

- ที่ 1,000 node ทุกขั้นตั้งแต่ s3 ขึ้นไปได้ผลใกล้ศูนย์ (ระดับต่ำไม่ได้ประโยชน์จาก search ใหม่)
- **ต่อ node ช้าลงรวมราว 20–25%** เทียบ s2 กับ s6 (~670 ms → ~835 ms) ส่วนใหญ่มาจาก LMR
- ตัวเลข Elo รายรุ่น **บวกกันตรง ๆ ไม่ได้** ผล s6 เทียบ s1 โดยตรงยังไม่ได้วัด และยังไม่ได้วัดที่เวลาเท่ากัน (engine ยังจำกัดด้วย node)
- ที่ราก PVS ลองแล้วไม่รับ (ดู EVALUATION.md)

## 10. สิ่งที่ยังไม่มี

จากโค้ดปัจจุบัน ไม่มีเทคนิคต่อไปนี้ (รายการเพื่อให้ทราบสถานะ ไม่ใช่งานที่กำหนดไว้ ดูลำดับใน [ROADMAP.md](ROADMAP.md)):

- ตารางจำที่เก็บข้ามตา (ตอนนี้สร้างใหม่ทุกครั้งที่ `go`)
- aspiration window, check extension, futility / delta pruning
- SEE (static exchange evaluation) ในการเรียงการกิน
- ตรวจเสมอเพราะหมากไม่พอ (เช่น คิงเดี่ยวสู้คิงเดี่ยว)
- การค้นหาด้วยเวลา (ตอนนี้จำกัดด้วย node เท่านั้น)
- โค้ดที่ไม่จัดสรรหน่วยความจำ (ยังใช้ `Vec` ต่อ node จึงใช้ในเฟิร์มแวร์ `no_std` ไม่ได้)
