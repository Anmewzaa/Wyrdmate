# สถานะและแผนงาน

สถานะของโครงการ ณ วันที่ผลวัดล่าสุด (2026-11-21) เมื่อสถานะเปลี่ยน ให้แก้ทั้งไฟล์นี้และ `CLAUDE.md`

## 1. เสร็จแล้ว

| รายการ | สถานะ |
|---|---|
| engine | search s1–s9 + UCI + node limit ([SEARCH.md](SEARCH.md)) |
| net inference | NNUE พร้อม accumulator แบบ incremental ([NET.md](NET.md)) |
| datagen / trainer | self-play และ training ด้วย bullet บน GPU ([TRAINING.md](TRAINING.md)) |
| net 6 รุ่น | `wyrd-i` (ผู้เล่นสร้างข้อมูลเท่านั้น) ถึง `wyrd-vi` (**ปัจจุบัน**: +47 ± 25 Elo เทียบ wyrd-v) |
| เครื่องมือวัดผล | `ab.ps1` (A/B, เวลาเท่ากัน), ladder, เทียบ Stockfish, หน้า `monitor.py` ([EVALUATION.md](EVALUATION.md)) |
| เว็บเดโม | `web/` + GitHub Pages ใช้ `wyrd-vi` เป็นค่าเริ่มต้น |
| ladder ปัจจุบัน | วัดแล้วกับ `wyrd-vi` + s9: 51,200 node = +549 Elo เทียบ 1,600 node ([EVALUATION.md](EVALUATION.md) ข้อ 5) |

ผลที่เพิ่มต่อรอบ: +115, +81, +31, +64, +47 Elo และรอบ 7 (`r7a`) ไม่ผ่านเกณฑ์ที่ 50,000 node จึงไม่รับ ([TRAINING.md](TRAINING.md) ข้อ 5)

## 2. งานที่เหลือ

| ลำดับ | งาน | สถานะ | หมายเหตุ |
|---:|---|---|---|
| 1 | hidden size (16, 64, 128 เทียบ 32) | **ทำแล้ว** | net ใหญ่ขึ้นไม่คุ้มที่เวลาเท่ากัน คง 32 ([EVALUATION.md](EVALUATION.md) ข้อ 8.1) ยังไม่ได้ลองหลาย hidden layer หรือ feature ละเอียดขึ้น |
| 2 | ปรับ search ต่อ | เปิดอยู่ | ปรับ margin ของ futility/delta ที่ยังไม่เคยปรับ, TT ข้ามตา, SEE ใน capture ordering, aspiration window ([SEARCH.md](SEARCH.md) ข้อ 10) |
| 3 | datagen คุณภาพสูงขึ้น | ยังไม่ทำ | ลอง node ต่อ move สูงขึ้น (เช่น 20,000) หรือข้อมูลมากขึ้นต่อรอบ เพื่อดูว่าคอขวดคือคุณภาพข้อมูลหรือไม่ |
| 4 | distillation | ยังไม่ทำ | เทรน net ใหญ่ของเราเองเป็นครูให้ net เล็ก (ยังอยู่ในแนว self-play ต้องบันทึกที่มาตามกฎเหล็กข้อ 1) |
| 5 | input feature ที่ฉลาดขึ้น (เช่น king buckets) | ยังไม่ทำ | แลกกับ RAM |
| 6 | วัด Stockfish ใหม่ | ยังไม่ทำ | ตัวเลขใน [EVALUATION.md](EVALUATION.md) ข้อ 6 เป็นของ wyrd-iv + s6 |
| 7 | **firmware `no_std`** | **เลื่อนไว้ ยังไม่มีบอร์ด ESP32** | ดูข้อ 3 |

ลำดับที่แนะนำ: ข้อ 3 ก่อน (ถูกและตอบคำถามว่าคอขวดคือคุณภาพข้อมูลหรือไม่) ถ้าไม่ช่วย แปลว่าวงวนตันจริง จึงไปทำ firmware

## 3. firmware (เลื่อนไว้)

ยังไม่มีบอร์ด ESP32 และยังไม่ได้เลือกชิปเป้าหมาย ตัวเลขความเร็ว RAM และเวลาต่อ move บนบอร์ดต้องมีบอร์ดจริงจึงวัดได้ ก่อนนั้นเป็นการประมาณทั้งหมด

**ที่ทำได้ก่อนโดยไม่ต้องมีบอร์ด:**

- แก้ search ให้ไม่ใช้ `Vec` และไม่ clone กระดานต่อ node (ประวัติ hash, `tried_quiet`, รายการ move) เป็นบัฟเฟอร์ขนาดคงที่ ผลต้องเหมือนเดิม
  (test เดิมผ่าน และ A/B match ไม่แพ้)
- ตรวจว่า engine ส่วน search/eval build ผ่านแบบ `no_std` ด้วย target ของ ESP32 (`cargo check`)

**ข้อกำหนดของ firmware (กฎเหล็กข้อ 5):**

- `#![no_std]` และอยู่นอก workspace (build ด้วย target ของ ESP32 แยก)
- weights `i16`/`i8` และ accumulator แบบ incremental
- ไม่จัดสรรหน่วยความจำ (allocation) ใน hot path ของ search
- ผลลัพธ์ต้องตรงกับ engine บนพีซีทุกตำแหน่งก่อนลงบอร์ด (ใช้ `examples/validate.rs` เป็นแนวทาง)
- ฝังไฟล์ net ด้วย `include_bytes!` และติด tag เวอร์ชันที่ flash ลงบอร์ด (D-007, D-008)
- งบ RAM ต้องนับ: net 49 KB, TT 64 KB, history 16 KB, accumulator < 1 KB จากทั้งหมด ~520 KB
- เมื่อมีบอร์ด: เลือกชิป (ESP32-C3/C6 เป็น RISC-V ติดตั้งง่ายกว่า, ESP32 ดั้งเดิมเป็น Xtensa ต้องใช้ `espup`) แล้ววัด node ต่อวินาทีจริง เพื่อกำหนด `node_limit` ที่ให้เวลาต่อ move พอดี
  และ engine ยังต้องมี time management (ตอนนี้จำกัดได้แค่ node)

## 4. ความเสี่ยงและข้อสังเกต

- ยังไม่เคยรันบนบอร์ดจริง
- ข้อมูลเทรนรอบแรกเสมอสูง (~80%) คำอธิบายใน D-010 ยังเป็นสมมติฐานที่ไม่ได้ทดสอบแยก ควรทบทวน `wdl = 0.0` ถ้าข้อมูลไม่ได้เสมอเป็นส่วนใหญ่อีกต่อไป
- ผลวัดทั้งหมดเทียบกับรุ่นก่อนของโครงการเอง ส่วนเทียบ Stockfish เป็นค่าประมาณหยาบ
- กำไรต่อรอบการเทรนลดลง ขนาด net ไม่ใช่คอขวดตามผลข้อ 8.1 ที่เหลือคือคุณภาพข้อมูล (ข้อ 2 ลำดับ 3 ตอบข้อนี้) ซึ่งยังเป็นข้อสันนิษฐาน
