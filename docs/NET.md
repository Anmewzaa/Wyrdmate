## 1. net ทำอะไร

engine หมากรุกต้องตอบคำถามเดียวซ้ำ ๆ ว่า **"ตำแหน่งนี้ ใครได้เปรียบเท่าไร"** คำตอบเรียกว่า evaluation เป็นตัวเลขหน่วย centipawn (cp)
โดย 100 cp ≈ ได้เปรียบเบี้ยหนึ่งตัว และเป็นค่าจากมุมมองของฝ่ายที่ถึงตา (side to move)

มีสองวิธีให้คะแนน:

| วิธี | อธิบาย |
|---|---|
| **material eval** | เขียนกฎเอง เช่น queen = 900, pawn = 100 แล้วรวมคะแนน หยาบ มองไม่เห็นเรื่องตำแหน่งของหมาก |
| **net** | โปรแกรมเล็ก ๆ ที่ **เรียนรู้** วิธีให้คะแนนจากตัวอย่างหลายล้านตำแหน่ง แทนที่จะเขียนกฎเอง |

net **ไม่ได้เลือก move** หน้าที่แบ่งกันดังนี้:

| ส่วน | หน้าที่ |
|---|---|
| **search** | ลองเดินทุก move ที่เป็นไปได้ คิดล่วงหน้าหลาย ply แล้วเลือก move ที่นำไปสู่ผลดีที่สุด ([SEARCH.md](SEARCH.md)) |
| **net** | ให้คะแนน "ตำแหน่งปลายทาง" ที่ search ไปถึง |

ตัวอย่าง: search ลองให้ queen ไปกินหมากตัวหนึ่ง แล้วลองต่อว่าอีกฝ่ายตอบอย่างไรอีกหลายชั้น เมื่อถึงปลายทางจึงเรียก net ให้คะแนน
แล้วเลือก move ที่ปลายทางมีคะแนนสูงสุดสำหรับฝ่ายเรา (โดยสมมติว่าคู่ต่อสู้เล่นดีที่สุด) ถ้าเลือก move จากคะแนนตำแหน่งทันทีโดยไม่คิดล่วงหน้า
จะถูกหลอกง่าย เช่น queen กินเบี้ยได้ดูดี แต่ ply ถัดไปถูกจับตาย

กฎหมากรุก (move ไหนถูกกติกา) อยู่ในไลบรารี `cozy-chess` net ไม่รู้กฎ รู้เพียงว่าตำแหน่งลักษณะใดมักดีหรือไม่ดี

## 2. โครงสร้าง

โครงสร้างที่ใช้ทุก net ตอนนี้คือ `(768 → 32) × 2 → 1`

```text
กระดาน ─▶ input layer 768 ค่า (0/1) ─▶ hidden layer 32 neurons ─┐
(มุมมองฝ่ายที่ถึงตา)                                            ├─▶ output layer ─▶ คะแนน 1 ค่า
กระดาน ─▶ input layer 768 ค่า (0/1) ─▶ hidden layer 32 neurons ─┘
(มุมมองอีกฝ่าย)
```

| ส่วน | ขนาด | หน้าที่ |
|---|---|---|
| **input layer** | 768 | กระดานที่แปลงเป็นตัวเลข: 6 ชนิดหมาก × 2 สี × 64 ช่อง แต่ละค่าบอกว่า "ช่องนี้มีหมากชนิดนี้สีนี้ไหม" (1 = มี, 0 = ไม่มี) |
| **hidden layer** | 32 | ชั้นกลาง แต่ละ neuron จับ "รูปแบบ" หนึ่งอย่างจากกระดาน |
| **output layer** | 1 | รวมผลของ hidden layer ทั้งสองมุมมองเป็นคะแนนเดียว |
| **perspective** | 2 | มองกระดานจากฝ่ายที่ถึงตา (STM) และจากอีกฝ่าย (NTM) ใช้ weights ของ hidden layer ชุดเดียวกัน |

"layer" คือชั้นหนึ่งของ network ส่วนที่เรียกว่า "ขนาด net" ในเอกสารนี้หมายถึง **hidden size** คือจำนวน neuron ใน hidden layer (ตอนนี้ 32)

## 3. neuron และ weights

**neuron** หนึ่งตัวใน hidden layer ทำสามอย่าง:

1. ดูค่าทั้ง 768 ค่าจาก input layer
2. คูณแต่ละค่าด้วย **weight** ของมัน แล้วบวกรวมกัน แล้วบวก **bias** (ค่าคงที่ของ neuron นั้น)
3. ผ่าน **activation function** แล้วส่งผลต่อไป

เนื่องจาก input เป็น 0/1 การคูณจึงเท่ากับ "เลือกบวกเฉพาะ weight ของช่องที่มีหมากอยู่" เท่านั้น

ตัวอย่างความหมาย: neuron ที่มี weight สูงที่ "คิงขาวอยู่ g1" และ "เบี้ยขาวอยู่ f2, g2, h2" จะมีค่าสูงเมื่อเจอ **คิงที่ปลอดภัยหลังกำแพงเบี้ย**
(เป็นตัวอย่างเพื่อให้เห็นภาพ ไม่ได้ตรวจว่า neuron จริงของเรา neuron ไหนจับอะไร)

| คำ | ความหมาย |
|---|---|
| **weights** | ตัวเลขที่ **เรียนรู้ได้** คือ "ความรู้" ทั้งหมดของ net เก็บในไฟล์ `.bin` ตอนเล่น **คงที่ ไม่เปลี่ยน** |
| **bias** | ค่าคงที่ที่บวกเพิ่มในแต่ละ neuron (และใน output) ก็เรียนรู้ได้ |
| **activation function** | ฟังก์ชันที่ทำให้ net จับความสัมพันธ์ที่ไม่ใช่เส้นตรงได้ ที่นี่ใช้ **SCReLU** = `clamp(x, 0, QA)²` (จำกัดค่าให้อยู่ใน 0..QA แล้วยกกำลังสอง) |

weights ไม่ได้ถูกเขียนโดยคน ตอนเริ่มเป็นค่าสุ่ม แล้วถูกปรับทีละน้อยตอน **training** ให้คะแนนที่ net ทายใกล้ค่าจริงในข้อมูลขึ้น ดู [TRAINING.md](TRAINING.md)

## 4. ทำไมต้องมี hidden layer

hidden layer คือที่ที่ net **สร้างแนวคิดของตัวเอง** แต่ละ neuron เป็น "ตัวตรวจจับรูปแบบ" หนึ่งอย่าง (เช่น คิงปลอดภัย, เบี้ยโดดเดี่ยว,
หมากรวมกันกลางกระดาน) แล้ว output layer รวมรูปแบบทั้งหมดเป็นคะแนนเดียว เรียกว่า "hidden" เพราะอยู่ระหว่าง input กับ output เรามองไม่เห็นตรง ๆ
ว่าแต่ละ neuron เรียนรู้อะไร

ถ้าไม่มี hidden layer net ก็รวม weights ของแต่ละช่องตรง ๆ ได้แค่ "หมากตัวนี้ช่องนี้มีค่าเท่านี้" ซึ่งใกล้เคียงกับ material eval ที่มีตารางช่อง
แต่จับความสัมพันธ์ระหว่างหมากหลายตัวไม่ได้

## 5. NNUE: ทำไมเร็วพอสำหรับ ESP32

**NNUE** (Efficiently Updatable Neural Network) คือ net แบบพิเศษของ engine หมากรุก input เป็น 0/1 และแต่ละ move เปลี่ยนหมากเพียง 1–2 ตัว
engine จึงไม่ต้องคำนวณ hidden layer ใหม่ทั้งหมดทุกตำแหน่ง แต่เก็บผลรวมก่อน activation ไว้ใน **accumulator** แล้ว **ปรับเฉพาะส่วนที่หมากเปลี่ยน**
(incremental update: ลบ weights ของช่องที่หมากจากไป บวก weights ของช่องที่หมากไปถึง) ทำให้ search เร็วขึ้นราว 30% ตามที่วัดไว้
(ผลจาก incremental ตรงกับการคำนวณใหม่ทั้งกระดาน มี test ใน `engine/src/nnue.rs`)

ความต่างจาก neural network ทั่วไป: ขนาดและ activation ที่เลือกเป็นเรื่องพื้นฐานของ neural network ทุกชนิด ส่วน "อัปเดตเฉพาะส่วนที่เปลี่ยน"
เป็นเคล็ดลับเฉพาะของ NNUE

## 6. Hidden size: ขนาดของ net

hidden size ไม่ได้ทำให้ training "คำนวณ weights ได้ดีขึ้น" แต่กำหนดว่า net **มี weights กี่ตัวให้เก็บความรู้** (เรียกว่า capacity)
เปรียบเหมือนสมุดโน้ต: training คือการจดลงสมุด hidden size คือความหนาของสมุด

จำนวนค่าที่เก็บ = `768 × H + H + 2 × H + 1` (H = hidden size) ขนาดไฟล์คำนวณจากสูตรนี้ ไม่นับ padding ท้ายไฟล์:

| H | จำนวนค่า | ขนาดโดยประมาณ | หมายเหตุ |
|---:|---:|---:|---|
| 16 | 12,337 | 24.7 KB | |
| **32** | 24,673 | **49.3 KB** | **ที่ใช้อยู่** (ไฟล์จริง 49,408 ไบต์รวม padding) |
| 64 | 49,345 | 98.7 KB | |
| 128 | 98,689 | 197.4 KB | เกือบ 40% ของ SRAM ทั้งหมดของ ESP32 (~520 KB) |

**ใหญ่ขึ้นไม่ได้ดีขึ้นเสมอ:**

| | hidden size เล็ก | hidden size ใหญ่ |
|---|---|---|
| ความละเอียดที่จับได้ | หยาบ อาจพลาดรูปแบบ | ละเอียดกว่า |
| ไฟล์ / RAM | เล็ก | ใหญ่ขึ้นตามสัดส่วน |
| ความเร็ว | เร็ว | ช้าลง (คำนวณต่อตำแหน่งมากขึ้น) |
| ข้อมูลที่ต้องใช้ | น้อยกว่า | ต้องการมากกว่า ถ้าน้อยเกินไปอาจเกิด overfitting (จดจำตัวอย่างแทนที่จะสรุปรูปแบบ) |

อีกทางคือเพิ่ม **จำนวน hidden layer** (ลึกขึ้น) ซึ่งจับรูปแบบซับซ้อนกว่าแต่ช้ากว่า NNUE ของหมากรุกมักใช้ hidden layer ใหญ่ชั้นเดียวเพื่อความเร็ว โปรเจกต์นี้ก็เช่นกัน

**ผลทดสอบ (2026-11-21):** เทรน H = 16, 64, 128 เทียบ 32 ด้วยข้อมูลเดียวกัน ([EVALUATION.md](EVALUATION.md) ข้อ 8.1) loss ลดลงตามขนาด แต่ Elo ที่ node เท่ากันเพิ่มไม่มาก
(H = 128 ราว +30) และที่เวลาเท่ากัน net ที่ใหญ่กว่า 32 ไม่คุ้ม (H = 64 เท่ากัน, H = 128 แย่กว่า) จึงคง **H = 32** ขนาดอื่นเทรนด้วย `wyrdmate-trainer ... <net_id> <hidden>` (อาร์กิวเมนต์ที่ 7)
กำไรต่อรอบการเทรนที่ลดลง ([TRAINING.md](TRAINING.md) ข้อ 6) จึงไม่น่าใช่เพราะ 32 เล็กเกินไป น่าจะเป็นที่คุณภาพ/ความหลากหลายของข้อมูลมากกว่า (ยังเป็นข้อสันนิษฐาน)

## 7. Input features

การแปลงตำแหน่งเป็น input ต้องตรงกับ `Chess768` ของ bullet ทุกประการ:

- หมากของฝ่ายที่ถึงตาถือเป็น "ฝ่ายเรา" (feature 0–383) หมากของอีกฝ่ายเป็น feature 384–767
- เมื่อฝ่ายดำถึงตา กระดานถูกพลิกแนวตั้ง (`ช่อง ^ 56`)
- perspective ที่สอง (NTM) คือพลิกแนวตั้งพร้อมสลับสี
- index ของ feature = `ออฟเซ็ตสี + 64 × ชนิดหมาก + ช่อง`

## 8. Quantisation

การเทรนใช้ weights เป็นทศนิยม แต่ไฟล์ที่ใช้จริงปัดเป็นจำนวนเต็ม `i16` เพื่อให้ไฟล์เล็กและคำนวณบน microcontroller ได้เร็ว เรียกว่า **quantisation**

| ค่าคงที่ | ค่า | ใช้กับ |
|---|---|---|
| `QA` | 255 | weights และ bias ของ hidden layer (`l0w`, `l0b`) |
| `QB` | 64 | weights ของ output layer (`l1w`) |
| `QA × QB` | 16,320 | bias ของ output layer (`l1b`) |
| `SCALE` | 400 | แปลง output เป็น cp |

สูตรใน `engine/src/nnue.rs`:

```text
out = Σ screlu(us[i]) · w[i] + Σ screlu(them[i]) · w[H+i]
out = out / QA + l1b
score_cp = out · SCALE / (QA · QB)
```

## 9. รูปแบบไฟล์ `quantised.bin`

ไฟล์ไบนารี little-endian ของ `i16` เรียงต่อกัน:

| ลำดับ | ชื่อ | ขนาด (จำนวน i16) | ตัวคูณ |
|---|---|---|---|
| 1 | `l0w` weights ของ hidden layer (เรียงตาม feature) | 768 × H | QA |
| 2 | `l0b` bias ของ hidden layer | H | QA |
| 3 | `l1w` weights ของ output layer | 2 × H | QB |
| 4 | `l1b` bias ของ output layer | 1 | QA × QB |

bullet เติมศูนย์ท้ายไฟล์ให้ขนาดเป็นพหุคูณของ 64 ไบต์ engine ตรวจว่าส่วนเกินน้อยกว่า 32 ค่า และคำนวณ H จากขนาดไฟล์อัตโนมัติ
(ยังไม่เคยทดสอบกับ H ที่ไม่ใช่ 32) สำหรับ H = 32 เนื้อหาจริง 49,346 ไบต์ ไฟล์ **49,408 ไบต์**

**งบหน่วยความจำบนบอร์ด** (ประมาณจากขนาดไฟล์ ยังไม่ได้วัดบนบอร์ดจริง):

| รายการ | ขนาดโดยประมาณ |
|---|---|
| weights ของ net (อ่านจาก flash ได้) | 49 KB |
| accumulator 2 perspective × 32 | น้อยกว่า 1 KB |
| SRAM ทั้งหมดของ ESP32 | ประมาณ 520 KB |

## 10. สถานะปัจจุบัน

net ที่ผ่านการรับอยู่ใน `nets/` (`wyrd-i` ถึง `wyrd-vi`) ทุกตัวมีโครงสร้างเดียวกัน (H = 32) ที่มาและผลแข่งของแต่ละตัวอยู่ใน [`../nets/RECORDS.md`](../nets/RECORDS.md)

การเปลี่ยนโครงสร้าง (hidden size, จำนวน layer, feature, `QA`/`QB`/`SCALE`) ต้องแก้ทุกฝั่งพร้อมกันและเทรนใหม่:
`trainer/src/main.rs` ↔ `engine/src/nnue.rs` ↔ `firmware/` (ดู [ARCHITECTURE.md](ARCHITECTURE.md) ข้อ 5)
